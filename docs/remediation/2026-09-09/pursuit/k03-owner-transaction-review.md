# K03 lifecycle owner transaction precondition and commit failure

Inspection found that lifecycle owner helpers documented a caller-owned transaction but did not enforce it. transfer_owner acquires a transaction-scoped advisory lock, reads the generation and updates the owner row. On an autocommit connection those are separate transactions, so the helper could lose serialization before its generation check/update. The same problem makes the local owner-token binding ineffective across statements.

lock_symbol now requires connection.is_in_transaction() to return True before executing SQL. Both bind_owner and transfer_owner pass through that guard. Explicit existing caller transactions remain required; the helper does not open or commit a replacement transaction. This protects the consumer, the candidate revision repository and legacy lifecycle persistence when it uses the shared owner binding. Raw legacy writers still depend on the existing managed-symbol database trigger; the new check is not a substitute for that trigger or evidence it ran.

Six local cases were added: rejection before any SQL for each of lock/bind/transfer on an autocommit protocol connection; transactional generation/token handover rejecting the old token; rollback on a simulated commit failure; and an authenticated ASGI request that receives HTTP 500 when commit fails, then succeeds on identical retry with one lifecycle/emission/inbox. The existing lost relay ACK and deduplication tests also pass. These are protocol-fake and TestClient observations, not real PostgreSQL or live TLS evidence.
