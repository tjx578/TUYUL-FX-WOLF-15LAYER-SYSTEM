# K07 capacity proposals, replay and release

The previous source supplied v3.1 TEST_ONLY parent sizing but no versioned capacity reducer. This slice connects that sizing to an immutable account ledger proposal with exact rational amounts, durable-style semantic reservation/plan/campaign/thesis identities, version checks and owner-epoch checks. It does not change the V1 reservation repository or any service entrypoint. Source SSOT sections 4 and 20 require semantic identity, monotonic handoff and actual atomic persistence; the last requirement remains unexecuted here.

The complete sizing request and expiry form a reservation envelope fingerprint. Identical retries return the stored current/terminal record without adding risk or incrementing version; changed payload under the same reservation ID conflicts. Duplicate retries may acknowledge a historical version, but a retired owner epoch is always rejected. New proposals require an exact current version, ledger receipt, snapshot/account/executor/policy binding and capacity total. The explicit TEST_ONLY slot policy is one parent per immutable thesis; tombstones prevent reuse after expiry/release. This is not an active risk-policy selection or strategy identity derived from the fingerprint.

HELD_UNISSUED can expire only at/after its expiry. MARK_DISPATCHED must be committed before any command may be delivered and changes the state to PENDING_RECONCILIATION. That state keeps its full planned risk even after expiry or timeout. Releasing it requires a scoped, fresh verified broker receipt AND a terminal delivery receipt: either confirmed cancellation with fencing and no broker effect, or reconciled terminal broker state. A report of no current fill while delivery can still run is insufficient. Identical release retries acknowledge the same terminal record; they never free risk twice or reopen it.

The baseline is independently verified exposure outside this ledger. Its source must exclude locally tracked reservations/positions, including dispatched ones. The reducer binds baseline clock/hash through the full ledger receipt; it does not collect or authenticate that provider. ExactAmountV31 now admits nonnegative rational totals in the sizing input as well as its existing Decimal form, so a fractional total such as 1/3 USD is not rounded at handoff. The successful result remains a proposed TEST_ONLY state with false reservation/execution authority.
