# K07 immutable candidate revision storage

Selected SSOT v3.1 section 17.7 forbids in-place mutation from advisory to canonical; section 20.1 requires locking a candidate revision before Transaction A. The existing candidate V2 repository has a different shadow-only identity contract. This slice adds a separate explicitly injected v3.1 repository and TEST_ONLY append receipt instead of rewriting V2 rows or generating active strategy authority.

Every new append binds full handoff content, predecessor hash and re-evaluation identity/receipt. Revision one has no predecessor. Later revisions increment exactly one, preserve plan/symbol/lifecycle/thesis/direction scope under the explicit TEST_ONLY revision policy, advance decision time, and require a new re-evaluation ID and receipt. Advisory-to-canonical additionally rebinds admission ID and receipt. A required verifier must attest the complete re-evaluation and individual authority clocks; hash references alone do not prove S3-S5 completion. Post-verification hashing rejects mutation. Active policy and domain proof provider remain unbound.

The PostgreSQL repository uses the same symbol owner fence as S03, validates an active transaction, locks latest revision, checks immutable duplicate content, and inserts the new receipt. append returns only after its injected transaction context commits; append_in_transaction returns a tentative record for future composition. An exact historical retry returns the old receipt without moving latest backwards or extending validity. lock_latest returns a stored fact, not current risk authority. No default database connection, owner election, bootstrap or runtime consumer switch is installed.

Migration 20260909_04 descends from 20260909_03 and defines immutable history keyed by plan/revision, globally unique re-evaluation IDs and a predecessor revision/hash foreign key. A trigger requires the shared owner token for insert, checks sequential revision, and rejects update/delete even for a current owner. Candidate non-execution flags and TEST_ONLY profile are constrained. This does not replace least-privilege database grants or full domain proof verification. No database migration was applied.
